# Customer Demo Factory

You turn **one customer URL** into a working, customer-relevant demo site built on the
`scdemos/demo` base. The solution consultant (SC) should have to do **one thing**: run
`/customer-demo <url>` after creating the site in **CloneIt** (which provisions the repo, Code Sync,
DA, config and publishing). Everything else is your job: brand, content, features and QA.
Do not stop to ask questions that you can answer yourself.

The base already ships the block library, section styles, experimentation/audiences/campaigns,
martech, dark mode, sidekick plugins, CloneIt, the demo walkthrough, and preflight checks.
**You reskin and refill it.** You do not rebuild it.

## Inputs: the URL is the only one

The SC provides **only the customer URL**, in any form: `https://www.x.com/a/b`,
`www.x.com/a/b`, `x.com/a/b`, or the bare domain `x.com`. Normalize it to `https://` and
follow redirects. Ignore extra words such as "demo", "for", "please" or "create". Derive everything else yourself and do **not**
ask. **The demo site is the repo you're running in**: read `git remote get-url origin` → `scdemos/<slug>`. An explicit `slug=<site>` in the prompt overrides it. Only when you run from the base `scdemos/demo` (or outside a repo) with no `slug=`, ask once which demo to customize.

**Everything lives in the `scdemos` space**, next to the base (`scdemos/demo`). This keeps
every customer demo in one place for tracking, observability and accounting. Never create
a demo in a personal account or in another org.

| Value | How to derive it | Example (acme-invest.com/institutional/us/en) |
|---|---|---|
| `slug` | Registrable domain without TLD or `www`, lowercase `[a-z0-9]`, max 20 chars. Add a short path hint when the URL is a sub-site. For CloneIt demos: the name of the repo you're in (`scdemos/<slug>`), generated by CloneIt from the customer **name**. | `acmeinvest` |
| GitHub repo | Always `scdemos/<slug>` | `github.com/scdemos/acmeinvest` |
| DA site | Always `scdemos/<slug>`, the same name as the repo, so the Config Service maps code → content automatically | `da.live/#/scdemos/acmeinvest` |
| Preview | `https://main--<slug>--scdemos.aem.page/` | |
| Page scope | Real pages only (F1), same slugs. **Always:** the SC's URL (home of the demo) and every top-nav page. **Plus what they depend on:** pages their CTAs and forms lead to (contact, thank-you), the footer's legal pages (privacy, terms, disclaimer) and one page per distinct template (article, event, product, fund). Typically 8–15; ask the SC once only if it exceeds 20. Never invent pages. | |
| Locale | From the URL path | `en` |
| Customer name | From `og:site_name`, otherwise the `<title>` brand, otherwise the domain | `Acme Investments` |

Announce the derived values in **one line**, together with the **commit approval** (P8):
"I'll create and commit to `scdemos/<slug>` (customer repo only). Base changes will be
proposed separately." Treat the SC's go-ahead (or the original prompt, if it already says
"go"/"autopilot") as approval for commits to the **customer repo only**. Then continue without
waiting.

**SC identity.** Roles and publish approvers need the SC's Adobe email. Read it with
`site-tab.js` `{ op: 'whoami' }` in the signed-in da.live tab (phase 0), falling back to
`git config user.email` when it ends in `@adobe.com`. Never guess it; if neither works, ask
once.

## Fidelity contract (non-negotiable, enforced by gates)

The demo is the customer's site rebuilt on the base: **same pages, same look, same words.** Five
rules, each with the gate that fails when it's broken. Don't hand off with a failing gate. The
fidelity checks can only be waived **by the SC** (`waivers.json` reason starting with `SC:`, e.g.
`"SC: licensed font, Source Sans 3 accepted"`); `compare.mjs` ignores any other waiver on them.
Environmental checks (`health` noise from third-party scripts) may carry the agent's own written
reason. The Lighthouse gate (100 on mobile and desktop) is waivable only by the SC.

| # | Rule | Enforced by |
|---|---|---|
| F1 | **Real pages.** Every demo page is a page of the customer site (same slug where possible). No invented pages, no base pages left live (they're backed up in 7a). | scope list from the SC's URL + nav; `lint:base-leftover`; `doctor:index` |
| F2 | **Real content.** Headings, copy, stats, CTAs, images and forms come from the original pages (`scrape/<page>/outline.json`, `assets/`). Never write filler copy. Allowed new text, outside the migrated pages only: a short "for illustration only" note on mocked data, block library and walkthrough docs, base UI strings (search, calculator, form messages, login labels) and gated-content teasers built from the page's own copy. | `compare:provenance`, `compare:headings`, `compare:text`, `compare:media` |
| F3 | **Same chrome.** The header has the original's anatomy (rows: utility bar / main nav / sub-nav; logo size and placement; sticky; search, region, login CTAs; the full dropdown / mega-menu tree from `design.json`). Same for the footer. | `compare:header layout`, `compare:header items`, `compare:footer links`, `compare:side rail` |
| F4 | **Same layout.** Section by section: alignment (centered vs left), text width, full-bleed bands, tone (dark/light), columns, and every carousel/slider, tab set and accordion. | `compare:layout`, `compare:carousels`, `compare:section count` |
| F5 | **Same look.** Type scale, button and card styles, container width and spacing follow `design.json`; verified by eye, page by page, original next to demo at 1440 and 390 px. | `compare --final` → `review.json` (one written verdict per page) |

## Operating principles (read first, apply in every phase)

These rules generalize every gotcha found so far. The phase rules below are applications of
them. When a phase rule doesn't cover a situation, apply the principle. Each principle has
automated checks: `scripts/doctor.mjs` (site health) and `scripts/lint-content.mjs`
(content models). Their failures print the principle ID.

| # | Principle | What it means in practice |
|---|---|---|
| **P1** | **Verify outcomes, not artifacts.** | A feature is done only after you've used it as a visitor would: typed a search, submitted every form (dry-run), opened the experiment/campaign URL (if set), clicked every nav, footer and in-page link, and changed calculator inputs. "The block renders" is not "the feature works". |
| **P2** | **The template copies code, not state.** | A repo made from the template has none of the base's per-site state: site config (`query.yaml`, `headers`, `robots`, `sidekick`, `public`, `features`), roles, the query index, the DA config/library, untracked icons, workers and secrets. Walk `references/base-state-inventory.md`: copy, recreate or explicitly skip every row. |
| **P3** | **Read the contract before reuse.** | Before using a block, worker, endpoint or plugin, read its content model and inputs (manifest, block JS, worker README). Never assume something is "generic". If it doesn't fit, choose another construct or make it generic at the source. Never force content into the wrong model. |
| **P4** | **Content parity before polish.** | Migrate every section of every page in scope (headings, copy, lists, stats, images, CTAs, forms, embedded widgets) before styling. Compare against the original's outline (`extract-outline.js`). A missing section is a FAIL, not a polish item. |
| **P5** | **Judge what renders, where it renders, under hostile conditions.** | Measure the painted result in a real browser: dark OS preference, 390 px and 1440 px, local code (`aem up`, no CDN cache), after lazy/reveal loading, with smooth scroll. Never infer looks from DOM ancestry or source. |
| **P6** | **Decide every base assumption.** | The base is opinionated (theme, currency/locale, casing, radius, gradients, accent bar, social dock, color literals, control styles). Walk `references/base-assumptions.md` and set each one to the customer's value, or confirm it. Nothing is inherited by accident. |
| **P7** | **Generic, opt-in, ported back.** | New constructs are variants, section styles or metadata switches with generic names. They're recorded in the manifest, ported to the base, and leave the base's default look unchanged (verified). Customer specifics live in content and tokens, never in code. |
| **P8** | **Zero side effects on shared systems.** | Automated checks use dry-run/test modes (`x-dry-run: 1` on the forms endpoint). Never post to live channels, inboxes or analytics. Commits go to the customer repo under the one-time approval; anything touching the base (`scdemos/demo`) needs its own explicit approval and goes in as a PR. |
| **P9** | **Encapsulate workarounds; verify the verifier.** | A tool quirk becomes a script or helper (see the scripts), not a paragraph to remember. Every new check gets a negative test: break the thing on purpose and confirm the check fails. |
| **P10** | **Every gotcha gets a prevention.** | In the retro (phase 11), map each new gotcha to a principle and a prevention: a base fix, a `doctor`/`lint-content` check, or a rule. "Documented only" counts as not prevented yet. |

## Reference files

- `references/demo-manifest.json`: the blocks, variants, section styles, brand slots and
  features the base provides. **Read it before mapping anything.**
- `scripts/preflight.mjs`: checks the customer site, the destination repo, Code Sync and DA.
- `scripts/lighthouse.mjs`: **last gate before sign-off** (phase 10b). Lighthouse on the published site, mobile + desktop, every scoped page: Performance, Accessibility and Best Practices must be 100 (SEO reported, not gated); writes the scores and a fix list.
- `scripts/parity.mjs`: **definition of done** (phase 10a). Drives capture + compare for every scoped page at 1440/390 + dark, on localhost, and writes the parity matrix and fix list.
- `scripts/capture.mjs` + `scripts/compare.mjs`: fidelity gate. They capture the original
  and the demo (screenshots plus a structural inventory per section) and produce
  `fidelity.html` with PASS/FAIL per page.
- `scripts/extract-outline.js`: in-page outline extractor for the original pages (no
  content dropped).
- `references/signoff-checklist.md`: the mandatory checklist before handoff. The SC
  maintains this list.
- `references/base-state-inventory.md` (P2): per-site state the base relies on, how to copy it and how to verify it.
- `references/base-assumptions.md` (P6): base defaults that need a customer decision.
- `scripts/doctor.mjs`: site health checks (P1, P2, P6, P8). Run it after phase 1, after phase 8 and in the final sweep.
- `scripts/lint-content.mjs`: DA content-model linter (P3). Run it before every bulk preview.
- `scripts/da-config.mjs`: migrates every DA config sheet from the base, rewritten for the customer (P2).
- `scripts/setup-check.mjs`: machine/harness check; `--fix` installs Playwright + matching Chromium outside the repo (phase 0).
- `scripts/scrape.mjs`: renders the original pages in a real browser; outline, brand, rendered images (phases 3/3b).
- `scripts/admin.mjs`: AEM Admin API without a browser: preview, publish, unpublish, unindex, code sync, status, config.
- `scripts/browser/site-tab.js`: DA + AEM Admin API from the signed-in da.live tab (no tokens): whoami, list, move, bulk preview/publish/unpublish, status, code sync, base backup.
- `scripts/browser/design.js` / `inventory.js`: in-page probes (design analysis; fidelity inventory) used by `scrape.mjs` / `capture.mjs` and runnable in the integrated browser.
- `scripts/docs-check.mjs`: keeps `SC-QUICKSTART.md` and the docs in sync with the skill (pre-commit).
- `SC-QUICKSTART.md`: the SC-facing one-pager. **Any change to SC-facing behavior (prompts,
  approvals, setup, outputs, troubleshooting) updates it in the same change**; `docs-check.mjs`
  blocks the commit until it's reviewed and stamped.

## Pipeline

Track each phase as a todo. Run the phases in order. Keep going until the handoff, unless you hit a ⛔ blocker.

**Run state (resume, never redo).** Keep `.customer-demo/run.json` in the demo repo (git-ignored)
and update it after every step: `{ site, customerUrl, scope: [{ original, demo, template, status }],
phases: { "<id>": "pending|running|done|failed" }, backup: { done, failed, purged }, waivers, notes }`.
On start, if it exists, **resume**: skip `done` phases and pages, re-verify anything `running`
(status calls, not blind retries), and never re-run the backup if `backup.done`. Report progress to
the SC in one line per phase ("3/9 · discovered 11 pages, design brief written"). The handoff
(phase 10) is generated from this file.

### 0. Environment check and the one sign-in (everything up front, never blocked later)
Do all of this **before** any work, in one go, and report only what needs the SC:
1. **Tools:** `node .skills/customer-demo/scripts/setup-check.mjs --fix` (Node, git, GitHub, AEM CLI,
   Lighthouse, `playwright-core` + the **matching** Chromium in `~/.cache/customer-demo`, never in
   `package.json`).
2. **The one sign-in (integrated browser).** Open `https://da.live/#/scdemos/<slug>` in the harness's
   browser (VS Code: `openBrowserPage`; Claude Code / others: Playwright MCP). If it shows the Adobe
   sign-in, ask the SC **once**: "Sign in to da.live in the browser tab I opened, then say done."
   Then run `site-tab.js` `{ op: 'whoami' }` → the SC's email and the token's remaining hours. That
   tab now covers **DA and the AEM Admin API** (da.live sends the IMS token to both), so no token is
   ever copied, pasted or printed. Keep the tab open for the whole run. The sign-in lasts about a
   day (`whoami` → `hours`); if fewer than 4 hours are left, have the SC sign in again now. If a
   call later returns 401, reload the tab, ask the SC once to sign in, and retry the same call.
3. **MCP servers** (declared in `.mcp.json`, `.vscode/mcp.json`, `.cursor/mcp.json`,
   `.codex/config.toml`, `.gemini/settings.json`; keep the server names `da` / `adobe-aem-ema` / `github` and
   the URLs identical in all of them): **DA** `da_list_sources(org: "scdemos", repo: "<slug>")`, **GitHub**
   `get_me`. If either fails, ask the SC to sign in to that server in their tool (same message as
   step 2). **EMA** is optional (scraping fallback). Gemini CLI and Codex don't preconfigure GitHub (it
   needs a token there): use `git` / `gh` with the SC's existing credentials for commits and pushes.
4. **Dev server:** `aem up` in the demo repo (phase 1b), so every browser test runs on
   **http://localhost:3000**.

Then work unattended: the only other reasons to talk to the SC are the ⛔ blockers in the failure
policy.

#### Harness capabilities (integrated browser first, scripts as the headless path)
Prefer the **integrated browser** for anything that needs a signed-in session or a look at a page:
the SC sees what happens, nothing needs a token, and the SC can answer a prompt in place. Use the
scripts when there's no browser in the harness, for long batch work (screenshots of every page),
and for the gates.

| Capability | Integrated browser (preferred) | Script path (any harness, headless) |
|---|---|---|
| Sign-in / SC identity | da.live tab + `site-tab.js` `whoami` | `git config user.email` |
| Preview / publish / unpublish / status / code sync | `site-tab.js` `bulk` / `status` / `code` in the da.live tab | `admin.mjs` with `DA_TOKEN` or `AEM_ADMIN_TOKEN` |
| DA documents, moves, media | DA MCP (`da_*`), or `site-tab.js` `list` / `move` | DA MCP |
| DA site config sheets | `mergeDaConfig` from `da-config.mjs` evaluated in the da.live tab | `da-config.mjs` with `DA_TOKEN` |
| Design analysis of the original | open the page, evaluate `browser/design.js` + `browser/inventory.js` | `scrape.mjs --headed` (writes the same files) |
| Look at the demo, use features (P1) | tab on `http://localhost:3000/<page>` at 1440 and 390 px | `capture.mjs --base http://localhost:3000` |
| Fidelity gate | (review screenshots side by side in tabs) | `capture.mjs` + `compare.mjs` (the gate itself) |
| Site health / content lint | n/a | `doctor.mjs`, `lint-content.mjs` |

How to evaluate a helper in the integrated browser: read the file, then
`runPlaywrightCode` → `return page.evaluate(<file contents>, { op: 'bulk', site: '<slug>', action: 'publish', paths })`
(raise `timeoutMs` for jobs). Browser tests always target **http://localhost:3000** (code from the
working copy, content from `main--<slug>--scdemos.aem.page`), never the CDN, which can serve stale
CSS for minutes after a push. If localhost isn't up, run `aem up` (phase 1b) first.
Never print or store tokens. Session/todo tracking: use the harness's task list if it has one;
otherwise keep a short checklist in the run report.

### 1. Attach to the demo site (CloneIt creates it) · P2

**Provisioning is not the agent's job any more.** The SC creates the site in **CloneIt**
(`https://da.live/app/scdemos/demo/tools/cloneit/cloneit`, signed in to da.live) and picks
**Customer demo**. CloneIt's worker, not the SC:
- creates `github.com/scdemos/<slug>` from the template and adds it to **AEM Code Sync**
  (SCs can't install apps in `scdemos`; the worker holds the org-owner token),
- makes the requesting SC (GitHub username, remembered by CloneIt) **admin** of the repo,
- creates the DA folder, copies the template content, **all DA config sheets** and the
  query index config, writes the AEM site config (SC as admin, `*@adobe.com`
  author/publish), and **previews + publishes** everything,
- records the demo in `da.live/#/scdemos/demo-registry` (audit log),
- hands the SC the prompt `/customer-demo <customer website URL>`, to run inside the new repo ("Open in VS Code"). CloneIt asks for the customer **name** only; the SC adds the website URL.

So the skill **attaches** to an existing site:

#### 1a. Check that the site exists
- The site is the current repo's `origin` (`scdemos/<slug>`), unless the prompt has `slug=`. In the base repo (`scdemos/demo`) with no `slug=`, ask once which demo; never customize the base itself.
- `git ls-remote https://github.com/scdemos/<slug>` must succeed, and
  `node .skills/customer-demo/scripts/doctor.mjs --site <slug> --only code,pages` must pass.
- **Doesn't exist?** Don't provision it yourself. Tell the SC in one line: "Create it first
  in CloneIt with site name `<slug>`, then come back", with the link above, and wait. Only if
  CloneIt can't create demos (not configured yet), use the fallback in **1e**.
- **Older repoless site** (created before CloneIt gave every demo its own repo; `code` points at
  `scdemos/demo`): the skill can only change **content** (phases 3, 7, 8 and 9b). Say so in one
  line, and offer "create a new demo in CloneIt" for code and design changes.

#### 1b. Start the dev server in the demo repo (the SC watches here)
Usually you're already in the demo repo (CloneIt's "Open in VS Code"). If not, clone it **next to the
SC's workspace** (never a hidden temp dir): `git clone https://github.com/scdemos/<slug>.git <workspace-parent>/<slug>`.
```bash
cd <demo repo> && aem up --no-open --forward-browser-logs   # detached/async, keep it running
```
(`aem` missing? `npm install -g @adobe/aem-cli`; `setup-check.mjs --fix` reports it.)
- Tell the SC in one line: "Watch it build at http://localhost:3000. Code is
  `<workspace-parent>/<slug>`."
- `aem up` serves **local code** with content proxied from `main--<slug>--scdemos.aem.page`.
  Every code change in phases 4–6 shows up live at localhost before it is pushed.
- **Do not add `fstab.yaml`.** The site config already points content at
  `https://content.da.live/scdemos/<slug>/`.
- Set `"project"` in `tools/sidekick/config.json` and the README Environments section to the
  `<slug>` URLs; commit with the SC's one-time approval (see Inputs). If no git credentials
  are available, use GitHub MCP `push_files`.

#### 1c. If code isn't served
`scripts/aem.js` returning 404 on aem.page means Code Sync hasn't synced the template
commit. Run `site-tab.js` `{ op: 'code', site: '<slug>' }` in the da.live tab (headless:
`DA_TOKEN=… node .skills/customer-demo/scripts/admin.mjs code-sync --site <slug>`), then re-check. If the repo isn't in Code Sync at all, an scdemos admin
must add it (Org settings → GitHub Apps → AEM Code Sync → Configure → add `<slug>`).

#### 1d. Verify the per-site state CloneIt created
CloneIt does the inventory rows S2–S6, S12 (config sheets) and S13 for you. Confirm with
`doctor.mjs --site <slug> --only state,index,search` (state needs the site config: `DA_TOKEN`, or
`--site-config` saved from the da.live tab), and fix gaps with
1d-2.

#### 1d-2. Recreate the per-site state the template doesn't carry (P2)
Creating a repo from the template copies **code only**. Walk
**`references/base-state-inventory.md`** row by row (site config, roles, query index, search
page, robots, sidekick, public, features, DA config and library, icons) and copy, recreate or
explicitly skip each one. Copied values must be **rewritten** where they point at the base
(hosts, `/scdemos/demo` path prefixes, other programs' DAM paths). Never copy `cdn`,
`apiKeys` or extra `access` entries. Then run `node .skills/customer-demo/scripts/doctor.mjs
--site <slug> --only state`. The index fills only on publish, so S4 and S5 pass after phase 7.

#### 1e. Fallback when CloneIt can't create demos
Use the issue workflow (`.github/workflows/provision-demo.yaml`): open an issue on `scdemos/demo` titled `new-demo: <slug>` (body: the customer URL, then `Customer: <name>`, label `demo-request`) and poll its comments for `provisioned ✅`. If that isn't configured either:
- Try GitHub MCP `create_repository` with `organization: "scdemos"`, name `<slug>`,
  `private: false`, `autoInit: false`. This works only for org admins.
  - On success: seed it from `scdemos/demo` with local git (clone the base, `rm -rf .git`,
    `git init -b main`, commit, push). Then an scdemos admin adds it to AEM Code Sync (see 1c).
  - On 403: send **one** message asking an `scdemos` admin to create the empty public repo
    `<slug>`, or to fix the provisioning setup. Include the issue link. Keep doing the
    non-repo phases meanwhile.

#### Access note
The demo uses customer assets. `.aem.page` is not indexed, so in the handoff call the
preview URL unlisted, not protected. If the SC wants authentication, link
https://www.aem.live/docs/authentication-setup-site.

### Failure policy (phases 0–1)

Talk to the SC before the handoff only when:
- the site doesn't exist yet (create it in CloneIt, see 1a)
- code isn't served and a full code sync didn't help (an admin must add the repo to Code Sync, see 1c)
- DA returns 401/403 for `scdemos/<slug>`

Each time, send **one** message with the exact link or action, then resume automatically.

### 3. Discover: deep analysis of the original · P4 P9 (F1–F5)
Enterprise sites often block bots (the first pilot's site returned 403 to `curl` and to DA's
server-side fetch), and many render client-side. **Always render in a real browser**, never
parse raw HTML. First open the SC's URL in the integrated browser, click through the nav (hover
every top item: dropdowns, mega menus, sub-navs) and pick the pages in scope (F1). Then:
```bash
node .skills/customer-demo/scripts/scrape.mjs --base <original origin+path> \
  --pages "/,/about,/products,…" --out scrape --headed
```
Besides content, it writes the **design analysis** per page (`<page>/design.json`,
`<page>/inventory.json`) and for the site (`scrape/design.json`): the full nav tree with hidden
children, header anatomy (rows, logo, sticky), type scale, button and card styles, container width,
section bands, per-section alignment/tone/columns and carousels. In the integrated browser, evaluate
`browser/design.js` and `browser/inventory.js` on any page for the same data.

Write a short **design brief** into the run report from these files before phase 4: header anatomy
(e.g. "white top bar, 80 px, logo left 52 px high, rail nav with 7 items, Capabilities has 5
children, search + region + 2 CTAs, not sticky"), the type scale, the 2 button styles, the card
style, the container width, and per page the section list (`#, pattern, alignment, tone, columns,
carousel?`), plus the **repeated sections** from `scrape/repeats.json` (CTA bands, newsletter
sign-ups, contact strips, disclaimers, "related insights"). Phase 5 maps every line of it; phase 10a checks every line again.
It renders each page, dismisses gates and cookie banners, slow-scrolls (lazy/reveal content),
and writes per page an `outline.json` (sections with headings, copy, lists, **tables, forms
with fields/options/required, embeds, background images, and `unknown` widgets** that keep
their text, so nothing is silently dropped) and a screenshot. It also writes `brand.json`
(colors by frequency, fonts, radius, logo, favicon, site name) and the images that were
actually rendered (`assets/` + `assets.json`).
- Choose the page scope with the Inputs rule (SC's URL, top nav, CTA/form targets, footer legal pages, one per template) and write it into the run state.
- Every `form` item in an outline is a form to migrate (Forms rule, phase 8). Every `unknown`
  item needs a construct decision in phase 5.
- Without `--headed`, headless Chromium may get a 403 or an empty page; use `--headed` for
  bot-protected sites. If both fail, fall back to EMA.

### 3b. Assets pipeline · P9
1. `scrape.mjs` already saved the rendered images, captured from the browser's own network
   responses: no CORS, no re-fetch, works on bot-protected CDNs. Resize large ones (≤1600 px).
2. Push them to a **temporary branch** `assets` of the (public) customer repo, and call
   `da_upload_media(sourceUrl: raw.githubusercontent.com/scdemos/<slug>/assets/<file>)`
   (DA can't fetch from customer CDNs). Use `sourceUrl`, not `base64Data`, to keep tool
   payloads small. Use the `alt` values from `assets.json`.
3. Delete the branch: `git push origin --delete assets`.
4. Logos are often SVGs with hidden embedded rasters. Prefer the site's header PNG wrapped
   in an `<svg><image href="data:…">` as `icons/logo.svg`.

### 4. Brand (reskin, no rebuild) · P6
Walk **`references/base-assumptions.md`** and decide every row; the steps below cover the brand rows.

Edit **only** the `BRAND TOKENS` block, the font tokens, `--border-radius-heritage`,
`--border-heritage` and `--shadow-glow-*` in `styles/styles.css`. Map the customer's colors
to the brand slots listed in `demo-manifest.json.brandSlots`. Do **not** rename tokens:
- primary → `--color-rust` (and the hover/lighter shade → `--color-rust-bright`)

### 5. Map: decide the right construct for every customer pattern · P3 P7

**Fidelity first.** Never squeeze a customer pattern into an existing block if the result
looks different from the original. Reuse is the means; matching the customer is the goal.
**Never drop content either**: if the original shows 8 news items, a grid/list toggle, a
carousel with 4 slides or a legal band, the demo shows them too.

For each section of each page, run `identify-page-structure` on the scrape. Then pick the
**lowest level that reproduces the pattern faithfully**:

| Level | Construct | Use when | Examples |
|---|---|---|---|
| 0 | **Default content** | Plain headings, text, lists, buttons, images. No repeating structure. | Intro paragraphs, disclosures, "Stay connected" CTA |
| 1 | **Existing block, as is** | The content model **and** the look match, apart from brand tokens. Read the block's content model first: `tabs` is **section-driven** (`Tab Id` / `Tab title` section metadata, not a table), `faq` reads `/faq-index.json`. | `table`, `form`, calculators, section-driven `tabs` |
| 2 | **Section style** (`section-metadata` style) | The difference is the section's background, width, spacing or alignment, whatever is inside. | `light`, `ink`, `center`, a new `bordered` band |
| 3 | **CSS-only block variant** | Same authoring table, different visual treatment or layout. | `cards text` / `list` / `stats`, `hero banner` |
| 4 | **Block variant with JS** | Same authoring table, but extra behavior gated on the variant class. Keep existing authoring backward compatible. | `cards list` + grid/list toggle, section-driven `tabs` with a `vertical` |
| 5 | **New block** | Different content model **or** behavior that would distort an existing block. Rule of thumb: over ~40% new CSS, a different row/column contract, or a new interaction model. | `carousel` (slides + prev/next + dots + autoplay), `consent`, `quote-slider`, `fund-finder` |
| 6 | **Global chrome variant** | Header, footer or page-frame layout differs: side-rail nav, utility bar, multi-column footer, legal band. Add a **variant of header/footer toggled by site metadata** (e.g. `nav-layout: rail`, `footer-layout: legal`); never fork the header. | Left icon nav rail, footer legal band (financial-services sites) |
| 7 | **Template** | A whole page type has its own structure: article, fund detail, event. | `templates/<name>/` + `Template` metadata |
| 8 | **Global feature / plugin** | Cross-cutting behavior configured by metadata, loaded lazily or delayed. | Consent manager, analytics, chat |

Decision rules:
- **Repeated content becomes a fragment.** A section that appears on 2+ pages (from
  `repeats.json`, or the same band you'd otherwise write twice) is authored **once** as
  `/fragments/<generic-name>` (e.g. `fragments/contact-cta`, `fragments/legal-disclaimer`) and placed
  on each page with a `fragment` block linking to it. Authors then edit it in one place, and the
  library lists it. `lint-content.mjs` fails (`lint:repeat-inline`) when the same section is
  written inline on two pages.
- Look for **variants of variants**: if two customer sections differ only in density or
  columns, use one variant plus a modifier class (`cards text two-up`), not two variants.
- **Name constructs generically** (`carousel`, `cards list`, `nav-layout: rail`), never
  after the customer, so the base can absorb them.
- New blocks follow `content-driven-development`. Write the authoring table first, then
  `building-blocks`. Default to no runtime dependencies, mobile-first, accessible
  (keyboard, ARIA, reduced motion).
- Every new construct goes into `references/demo-manifest.json` with its level, content
  model and use. Mark it `baseCandidate: true` if it's generic.
- When in doubt between levels 3 and 5, prototype the variant. If the CSS fights the
  base block (heavy `!important`, reordering DOM in CSS), switch to a new block.

Record the decision for **every line of the design brief** in session SQL (`page, section,
customer_pattern, level, construct, rationale, status`): every section of every page **plus** the
chrome rows (`header`, each nav item with children, `footer`, `type`, `buttons`, `cards`, `container`).
A row is `done` only after the construct exists and renders like the original on localhost:3000.
Nothing is skipped because the base has no match: an unmappable pattern gets a **new construct** at
the right level (variant, section style, block, chrome variant), named generically, and goes into
`references/demo-manifest.json` **and** the DA block library (phase 9b) so the SC can use it in the
demo. The QA loop (phase 9) and the final sweep (10a) compare section by section against this table.

   ```bash
   node .skills/customer-demo/scripts/parity.mjs --review fid/review.json   # P4 P5, F1–F5 + functionality (wraps capture + compare)
   ```
   All must exit 0, or every remaining FAIL is listed as ⚠️ in the report with its reason.
   `compare.mjs` is strict by default (no missing header/footer items, CTAs ≥ 80%, images ≥ 90%,
   copy ≥ 80%, all headings). A check may pass only through `--waivers waivers.json`
   (`{ "<page>|*": { "<check>": "reason" } }`), which is the closest-possible-alternative escape hatch:
   waivers are printed in the output and copied into the report. `--strict` turns SKIPs (e.g. no admin token) into FAILs, so unverified state can't pass. `--scope` is the demo's page list.
2. **State (P2):** walk `base-state-inventory.md`; every row is copied, recreated or skipped with a reason.
3. **Assumptions (P6):** walk `base-assumptions.md`; every row has a customer decision.

5. **Looks (P5):** every page at 1440 and 390 px under a dark OS. Look at every section

6. **Lighthouse:** the 10b gate (every page, mobile + desktop, 100 except SEO).
7. Fill in the sign-off checklist, with evidence for each item.

### 10b. Lighthouse gate: 100 on mobile and desktop (last pass before sign-off)
After parity passes and the pages are published, score **every scoped page** on the published site:
```bash
node .skills/customer-demo/scripts/lighthouse.mjs          # site + scope from .customer-demo/run.json
# → fid/lighthouse.md: scores per page × mobile/desktop + FIX LIST (audit, and the elements/URLs causing it)
```
**Performance, Accessibility and Best Practices must be 100 on both mobile and desktop** (median of
3 runs; SEO is reported only, the demo is noindex on purpose). Loop: fix → publish → rerun with
`--pages "<failing pages>"` → after code or layout changes, rerun `parity.mjs --pages` for those pages
too (a speed fix must not break fidelity). Typical fixes:
- **LCP / speed index:** the first section carries the hero image or lead copy (never a title-only
  section); the LCP image is the first image in the first section, sized ≤ 2000 px, no lazy CSS
  background; fonts have a metric-matched fallback (`size-adjust`).
- **CLS:** fixed height for the header/rail, images with dimensions, fonts with fallback metrics,
  no content injected above the fold after load (banners overlay, they don't push).
- **TBT:** third-party scripts (martech, chat, embeds) load in `delayed.js` or after consent, never
  in the eager or lazy phase; heavy blocks load their libraries on interaction.
- **Accessibility:** contrast from the brand tokens (fix the token, not the instance); icon-only
  links and buttons get an `aria-label` (from the icon name or the original's label); heading
  order; form labels; alt text from the original.
- **Best Practices:** no third-party cookies before consent (Web SDK / Target only after the
  consent banner's accept, or in `delayed.js` with consent defaults), no console errors or
  DevTools issues, images at the right aspect ratio and resolution.
Problems that come from the **base** (they show on `main--demo--scdemos.aem.live` too) are fixed in the
demo repo and **ported back** (6b) so every future demo starts at 100. After 3 rounds a page still
below 100 stays in the report with its scores and failing audits, and the SC decides.
The migration is done (and the backup may be purged) only when `parity.mjs` and `lighthouse.mjs`
both exit 0.

### 10. Handoff (the only long message to the SC)
Only after `parity.mjs` and `lighthouse.mjs` exit 0 (or every remaining ❌ has the SC's decision
recorded). Include `fid/parity.md` and the Lighthouse table from `fid/lighthouse.md`.

Generate it from `.customer-demo/run.json` (scope vs done, retries, waivers, failures). Report, in this order:
- Preview, live, DA edit and repo URLs.
- The parity matrix from 10a (page × design, content, look & feel, functionality, notices & login,
  base features), each cell ✅ / ⚠️ with a one-line note.
- The features baked in, and where to show them; how to add an experiment or campaign if the
  story needs one (not set by default).
- That the base demo backup was deleted after parity passed (the base demo stays in `scdemos/demo`),
  or why it was kept.
- Consent / disclaimer, login wording, gated pages and templates in use, and how to show them.
- The new constructs (blocks, variants, section styles) and where they are in the block library.
- Substitutions made: fonts, mocked data, skipped interactions.
- Manual follow-ups, which should be few: any brand sign-off, and an admin adding the repo to
  Code Sync only if code still isn't served.
- The demo walkthrough link.

### 11. Retro (every run, after handoff) (P10)
Append to the run's report (`references/pilot-reports/<slug>-<yyyy-mm>.md`; this folder is git-ignored, so the report is the operator's working notes and is never committed) a
**gotcha table**: `# | symptom | root cause | principle | prevention | status`. Prevention is
one of: **base fix** (code in `scdemos/demo`), **doctor:<check>**, **lint:<rule>**,
**gate** (compare/capture), or **rule** (SKILL.md text). Any gotcha whose only prevention is
"rule" is listed under "not yet prevented" and proposed as a script check or base fix. Gotchas
found by the SC rather than the agent are flagged: they show where the checks are blind.
Because reports stay local, **the retro is only done when its lessons land in shared files**: a principle or rule in SKILL.md, a check in `doctor.mjs` / `lint-content.mjs`, or a base fix, plus `SC-QUICKSTART.md` when it changes what an SC sees or does. Propose those changes to the SC (and commit only with their OK).

## Guardrails

- **Commit approval (P8):** customer work is committed to the customer repo (`scdemos/<slug>`, `main`) under the one-time approval given at the start. Anything for the base (`scdemos/demo`: generic variants, manifest, skill fixes) is prepared on a short feature branch and offered as a **pull request only after asking**; never commit or push to the base `main` directly.
- **No side effects on shared systems (P8):** automated form submits use `x-dry-run: 1`; never post to Slack, email or analytics on purpose.
- Never edit `scripts/aem.js`, `head.html` or `package-lock.json`. Never commit secrets.
- Branch names are at most 8 lowercase alphanumeric characters, e.g. `cardlogo`.
- Use conventional commits (`feat:`, `fix:`, `chore:`).
- Never fork a base block into a customer-specific copy. Use a variant instead.
- Keep customer assets out of the base `scdemos/demo` repo. They go only to the
  destination repo and DA.
- If a phase fails twice, record the failure, use a sensible fallback (a simpler block, a
  placeholder image, static data) and keep going. Report it in the handoff instead of
  stopping.
